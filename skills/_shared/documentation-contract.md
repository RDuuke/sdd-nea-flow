# Reader-Oriented Development Documents

Load for human-facing proposals, design explanations, guides and review
descriptions. No new phase, template gate or narrative audit file. Honor actual
project templates and Spanish artifact prose.

Lead with the decision, behavior or next action; follow with reasoning/evidence.
Start with the common path, then disclose conditional detail through sections
and links. Use tables for real comparisons and checklists for observable
acceptance, not decorative repetition.

For review-facing work, name the useful reading order: changed operative
contract/entry point, affected consumers, then evidence. Include material scope
and limits. Link real dependencies when work is chained, without requiring
chained PRs or a file-by-file conversation history.

Keep one canonical instruction location. Summaries link to operative sources;
examples never silently override them. Check the content consumers actually
receive, not just a mirror's existence or row count. Brief documents need no
fixed Quick path/Details/Checklist/Next step skeleton. Do not repeat guidance
in every phase or convert compact YAML into long Markdown.

Cite actual reports/commands/observations and pending work; a checked box alone
does not prove execution. Tool-free reviewers can analyze supplied bytes but
cannot claim runtime checks. Preserve strict phase JSON responses.
